# Sensitive tables — security matrix (Nautilo + Logto)

This versioned matrix records sensitivity, readers, and writers for the database
schema. Add a `nautilo` row in the same PR as every new exported Drizzle table;
`packages/db/tests/unit/sensitive-tables-matrix-complete.test.ts` verifies parity.
Classification notes describe their recorded implementation and must be
rechecked before changing access, encryption, or backup behavior.

## Classification taxonomy

Same four-level scheme as `sensitive-files-matrix.md` (adapted for relational tables rather than filesystem paths):

| Level | Meaning |
| --- | --- |
| **PUBLIC** | No meaningful confidentiality requirement — seed definitions, capability/role slugs, static metadata whose disclosure does not weaken authz or privacy guarantees by itself. |
| **OPERATOR-INTERNAL** | Deployment-private product data: transcripts, memories, artifacts, trust graphs, jobs, invites (hashed tokens), relay token hashes, profile rows, etc. Readable by the trusted server process and (today) any code path holding the single `nautilo` DB role — **D168 Path C RLS narrows agent-visible rows** on the namespace-scoped subset; backups still leak plaintext unless D129 P6 ships. |
| **CREDENTIAL** | Authentication factors, session-adjacent secrets, or hashes whose disclosure enables offline guessing / account takeover when combined with other leaks. Writers and readers must be cited concretely for forensics. |
| **EPHEMERAL-SECRET** | Values that exist in **raw** form only briefly (HTTP response, in-memory buffer) while the persisted row stores a **hash / ciphertext / token digest** instead. At the **table** grain we rarely mark whole tables EPHEMERAL-SECRET; see per-row notes. |
