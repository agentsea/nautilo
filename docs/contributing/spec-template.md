# Nautilo Contribution Spec

> This is a public, contributor-safe design artifact. Keep production
> implementation out of the spec pull request. Do not include private issue
> identifiers, internal planning links, real credentials, private Room content,
> or sensitive infrastructure.

`PROPOSED`

## Outcome

Who can do what after this change that they cannot do today? Explain why this
belongs in Nautilo rather than an external package or one-off automation.

## Verified current state

Describe only what you verified in the current repository. Cite each material
claim with `path:line` evidence and name the commit inspected.

## Proposed requirements

Mark every new requirement `PROPOSED` until maintainer approval.

## Constraints and non-goals

State the boundaries that keep the change coherent and the tempting adjacent
work this proposal deliberately excludes.

## Product and architecture fit

Trace the existing entities, owners, identity, data flow, permissions,
Capabilities, approvals, Rooms, Namespaces, Agents, and Connections affected.
Call out any trust boundary that changes.

## Unknowns and decision forks

Expose real unknowns. Present meaningful alternatives and their tradeoffs.
Do not manufacture certainty or quietly choose a product direction for the
maintainers.

## Implementation seams

Name the packages, apps, schemas, migrations, APIs, background work,
compatibility boundaries, and operator surfaces likely to change. This is a
map, not an implementation diff.

## Failure, recovery, and rollback

Describe denial, timeout, retry, partial success, cancellation, restart,
reconciliation, rollback, and data-recovery behavior that applies.

## Security and privacy

Describe secrets, external data movement, retention, logs, model exposure,
authorization, revocation, and abuse paths. Do not disclose a live
vulnerability in this public document.

## Interaction evidence

For UI, UX, or mobile work, include journeys, state transitions, ASCII or
visual wireframes, keyboard/focus behavior, accessibility, reduced motion,
narrow layouts, and all material failure and recovery states.

## Integration addendum

For a third-party integration, define integration mode, Connection ownership,
authorization and secret lifecycle, data boundary, Capabilities and approvals,
action semantics, failure recovery, UX, test strategy, compatibility, and
stewardship.

## Verification

Define automated tests, contract or fixture proof, manual QA, release-current
acceptance, documentation updates, migration checks, and cleanup. Every
requirement needs observable evidence.

## Delivery slices

Break the work into the smallest complete vertical outcomes. Enabling plumbing
is a sub-step, not a finished milestone by itself.

## Stewardship

Who intends to maintain this capability, its external dependencies, tests,
examples, compatibility claims, and release verification?
